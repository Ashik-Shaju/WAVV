# Wavv Music Understanding Implementation Research

Date: 2026-09-24

## Decision

Keep DyMN04-AS as the frozen-backbone **candidate baseline**, with Music Understanding separate from DCLAP. The checkpoint size and AudioSet score support a feasibility choice, not validated Wavv-task accuracy. Before training, correct the label/split plan and lock an artifact, preprocessing, and evaluation manifest.

## Human classification annotations: valuable training source; split carefully

MTG's pinned README explicitly describes the Music Classification Annotations as suitable for training individual classifiers. They are attached to **split-0 test** tracks, however, so any task trained from them needs a new artist-grouped train/validation/test split; reused tracks can no longer count as untouched split-0 test. The numbered MTG splits are alternate partitions, not mutually exclusive folds. I verified `track_0000214` occurs in split-0 test and split-1 train, and `track_0003112` occurs in test for both split-0 and split-1. Source links below pin snapshot `cafd8e20c265ed84f1e61f1c875327971f43a62f`: [annotation description](https://github.com/MTG/mtg-jamendo-dataset/blob/cafd8e20c265ed84f1e61f1c875327971f43a62f/derived/music-classification-annotations/README.md), [split generator](https://github.com/MTG/mtg-jamendo-dataset/blob/cafd8e20c265ed84f1e61f1c875327971f43a62f/scripts/data_split.py), [split-0 train](https://raw.githubusercontent.com/MTG/mtg-jamendo-dataset/cafd8e20c265ed84f1e61f1c875327971f43a62f/data/splits/split-0/autotagging-train.tsv), [split-0 validation](https://raw.githubusercontent.com/MTG/mtg-jamendo-dataset/cafd8e20c265ed84f1e61f1c875327971f43a62f/data/splits/split-0/autotagging-validation.tsv), [split-0 test](https://raw.githubusercontent.com/MTG/mtg-jamendo-dataset/cafd8e20c265ed84f1e61f1c875327971f43a62f/data/splits/split-0/autotagging-test.tsv), [split-1 train](https://raw.githubusercontent.com/MTG/mtg-jamendo-dataset/cafd8e20c265ed84f1e61f1c875327971f43a62f/data/splits/split-1/autotagging-train.tsv), and [split-1 test](https://raw.githubusercontent.com/MTG/mtg-jamendo-dataset/cafd8e20c265ed84f1e61f1c875327971f43a62f/data/splits/split-1/autotagging-test.tsv).

**Recommended protocol:** pin and verify the exact clean TSV, derive support from its parsed labels, and record README table differences as upstream documentation drift. Then create a separate artist-grouped fit/validation/test split from the human-annotated tracks, per task where taxonomies have different coverage. Any track used to fit or tune a human-label head is removed from that task's final evaluation. Keep those results distinct from the weak uploader-tag benchmark and never combine numbered official splits.

## Exact task coverage and label limits

The pinned clean TSV contains 15 taxonomies, but its acoustic-label key differs from the README: the README calls it `genre_acoustic`, while the TSV uses `mood_acoustic`. The exact TSV therefore has four `genre_*` fields, seven `mood_*` fields (acoustic plus six other attributes), danceability, voice/instrumental, gender, and tonal/atonal. Use the exact TSV key `mood_acoustic`; do not silently rename or reinterpret it as a genre. Published perfect-agreement support ranges from 180 to 8,756 tracks depending on taxonomy. A follow-up audit of both pinned raw and clean TSVs found 11,565 unique tracks in raw (the complete split-0 test set) and 10,671 in clean; filtering raw to three identical answers and excluding the documented special responses reproduces the clean-file support counts, but both files still disagree with the README table. Examples: Dortmund 621 vs. 612, voice 2,313 vs. 2,070, and tonal/atonal 7,424 vs. 8,756. An earlier parse had counted 6,639 `instrumental` answers under gender; the corrected audit records those separately and counts 2,074 male/female labels. The local clean TSV matches the exact pinned upstream file, so use its parsed counts operationally and record README differences as upstream documentation drift. Do not use the clean voice-only labels as binary vocal/instrumental supervision. The release does not provide human-validated instrument labels. [Pinned raw TSV](https://github.com/MTG/mtg-jamendo-dataset/blob/cafd8e20c265ed84f1e61f1c875327971f43a62f/derived/music-classification-annotations/music-classification-annotations-raw.tsv), [pinned clean TSV](https://github.com/MTG/mtg-jamendo-dataset/blob/cafd8e20c265ed84f1e61f1c875327971f43a62f/derived/music-classification-annotations/music-classification-annotations-clean.tsv), [pinned annotation README](https://github.com/MTG/mtg-jamendo-dataset/blob/cafd8e20c265ed84f1e61f1c875327971f43a62f/derived/music-classification-annotations/README.md).

- Use unanimous human annotations as candidate supervision for the exact taxonomies they cover. Keep the four genre taxonomies and seven mood attributes distinct; do not turn them into inferred broader labels.
- Use MTG uploader tags for weak genre, mood/theme, and instrument heads. The clean consensus TSV contains only `voice` after excluding `instrumental`; it cannot supervise a binary task without a defensible negative class. The gender taxonomy also contains unanimous `instrumental` answers and needs explicit filtering/semantics before use.


The [MTG dataset README](https://github.com/MTG/mtg-jamendo-dataset) describes the uploader-provided tags and official train/validation/test manifests. The human-label README provides the exact class lists and support counts above.

## Which related datasets fit this model?

- **Music Classification Annotations:** best match for supervised structured outputs. The upstream README explicitly says the consensus labels suit classifier training and lists 15 taxonomies. They are on split-0 test recordings, so build new artist-grouped splits and stop presenting reused tracks as untouched test data. Use the exact pinned TSV and record its differences from the README table.
- **Song Describer:** 706 recordings with about 1.1k captions; the official record marks it for music-language evaluation and lists a 3.3 GB audio archive. Useful if Wavv later adds captions or text/audio retrieval, not for the current tag/regression heads. [Zenodo record](https://zenodo.org/records/10072001).
- **MuChoMusic:** 1,187 human-validated multiple-choice questions on 644 tracks, designed to evaluate multimodal audio-language knowledge and reasoning. It needs a question-answering model; it does not supervise the current structured classifier. [Official benchmark](https://mulab-mir.github.io/muchomusic/).
- **ManyMusic-Stim:** human ratings include perceived valence/arousal, liking, being moved, familiarity, and professionalism from 200+ participants, making it a useful affective-data candidate. Its Zenodo audio bundle is 30.4 GB and the collection includes MTG-Jamendo-derived tracks, so it is not a compact independent test without track-level overlap checks. [Dataset overview](https://manymusic.net/stim/), [Zenodo bundle](https://zenodo.org/records/17425915).

For the constrained CPU workstation, use the human consensus annotations on the capped artist-grouped sample for covered tasks. The current 800-row manifest has no uploader-tag head meeting its floors, so keep those tags only as recorded metadata and do not train weak-tag heads in this first baseline. Do not use the existing 2,500/750/1,000 official-partition weak-tag sample as a fallback for this custom split. DEAM is deferred from the first baseline; consider it later for valence/arousal after defining its target alignment and checking cross-dataset duplicates. Do not add ManyMusic or caption/QA datasets to this classifier baseline.

## Model and input claims

The official [EfficientAT README](https://github.com/fschmid56/EfficientAT/blob/main/README.md) reports DyMN04-AS at 1.97M parameters, 0.12B MACs, and 45.0 mAP **on AudioSet**. That mAP is not evidence of Wavv genre, instrument, mood, or emotion quality. The pinned official DyMN implementation returns AudioSet logits plus a globally pooled final feature and can return intermediate feature maps. The reproducible CPU contract check in `music understanding/reports/backbone_contract.json` used source commit `a425fdce92572e602a1d5634799bd9f1f2efa806` and the official `dymn04_as.pt` checkpoint (8,086,973 bytes; SHA-256 `49b0e63577021994257b3de2ac5f1686d71554b93c8149f9d2568ad5760b904e`). It verifies 10-second mono 32 kHz input, `[-0.97, 1]` pre-emphasis, 1,024-point FFT, 800-sample window, 320-sample hop, 128 Kaldi mel bins, power mel, `ln(mel + 1e-5)` and `(mel + 4.5) / 5` normalization. The outputs are `[1, 1, 128, 1000]` mel, `[1, 527]` logits, and a finite/repeatable `[1, 384]` pooled feature. Only the pooled feature is a candidate Wavv input. The checkpoint has no separately stated license; do not redistribute it or a derived model until terms are confirmed.

The [Low-Complexity Audio Embedding Extractors paper](https://eurasip.org/Proceedings/Eusipco/Eusipco2023/pdfs/0000451.pdf) supports the general frozen-representation-plus-lightweight-head approach and 10-second scene pooling, but its reported feature-selection results are for **MobileNet**, not DyMN04-AS. Treat layer choice and song-window aggregation as hypotheses: compare the checkpoint's pooled feature first, and test an intermediate feature only if the first baseline is inadequate.

## Device-constrained CPU plan

**Documented facts:** MTG recommends its 320 kbps MP3 as the default, but provides a smaller mono version made from the same recordings with LAME VBR quality 2; the complete `raw_30s` collection is listed as 508 GB at full quality and 156 GB as `audio-low`. EfficientAT lists DyMN04-AS at 1.97M parameters and 0.12B MACs per its 10-second input setup, and explicitly presents the family for resource-constrained use and general-purpose audio representations. Its 45.0 AudioSet mAP is an AudioSet result, not a measurement on this laptop or Wavv labels. [MTG download and format details](https://github.com/MTG/mtg-jamendo-dataset#downloading-the-data), [EfficientAT model and complexity table](https://github.com/fschmid56/EfficientAT#pre-trained-models).

**Annotation coverage:** the pinned MTG README describes annotations for split-0 test, with genres covering only 1,500 recordings. Its 15 table counts are per-taxonomy unanimous/suitable labels, not disjoint sets of audio tracks. In our pinned files, the clean TSV has 10,671 unique track IDs, all present in split-0 test (11,565 tracks); the local TSV matches the exact pinned upstream file, so use its parsed counts and record the README differences as upstream documentation drift. Sources: [pinned annotation README](https://github.com/MTG/mtg-jamendo-dataset/blob/cafd8e20c265ed84f1e61f1c875327971f43a62f/derived/music-classification-annotations/README.md), [pinned clean TSV](https://github.com/MTG/mtg-jamendo-dataset/blob/cafd8e20c265ed84f1e61f1c875327971f43a62f/derived/music-classification-annotations/music-classification-annotations-clean.tsv), [pinned split-0 test TSV](https://github.com/MTG/mtg-jamendo-dataset/blob/cafd8e20c265ed84f1e61f1c875327971f43a62f/data/splits/split-0/autotagging-test.tsv).

**Recommendation for the 16 GB, CPU-only i5-1235U device:** use the human annotations on an artist-disjoint 800-track first baseline: 560/120/120 fit/validation/test, retaining seven binary `mood_*` TSV fields (including `mood_acoustic`) plus danceability at the minimum class/artist reporting floors. The 2026-09-24 Jamendo inventory found 4,915 allowed IDs, 228 explicit denials, and 5,528 IDs without metadata; those missing records are not treated as denials. The exact manifest report records that no uploader-tag head reaches the floor at this cap, and gender/tonal-atonic fail rare-class support. Keep 4,250 as an optional later expansion ceiling only if the validation baseline identifies a need. Do not stage MTG's 156 GB archive for this run. The 9-track OGG smoke check measured 16.48 seconds and 5.39 MB per newly processed full track on average, projecting roughly 3.7 hours and 4.3 GB for 800 if representative; the five-track format pilot estimated 2.77 GB from its median size rate. Treat both projections as noisy. Audio is acquired one file at a time, immediately deleted, and only 384-value features remain (1.17 MiB of raw float32 payload at 800 tracks). The class-support floors are reporting minima, not evidence of model accuracy; no public result proves this Wavv model will reach a particular target quality.

Freeze DyMN04-AS, download one OGG at a time, extract one deterministic 10-second mono 32 kHz midpoint window through the official frontend, cache its 384-value pooled feature, and delete the OGG. The 800-row raw feature payload is about 1.17 MiB; the optional 4,250-row ceiling is about 6.23 MiB. The 9-track smoke check passed with exact 320,000-sample windows, finite/repeatable features, and no audio left behind. Its measured transfer is much slower than the inference/frontend compute; the full cache is still processing. **Archive alternative:** MTG distributes audio in TAR archives, and its pinned downloader iterates over every archive for the requested dataset/type; it has no track-ID filter. `--remove` unpacks and removes each archive as it goes. The full 156 GB `audio-low` set is technically within the workstation's recorded free space, but it is not selected for the initial run because the per-track OGG API route avoids staging unrelated audio. [Pinned downloader source](https://github.com/MTG/mtg-jamendo-dataset/blob/cafd8e20c265ed84f1e61f1c875327971f43a62f/scripts/download/download.py), [download instructions](https://github.com/MTG/mtg-jamendo-dataset#downloading-the-data).

**Selected low-space acquisition route:** Jamendo's official `/tracks/file` API accepts one track ID and redirects to that track's audio. It requires a registered `client_id`, checks the per-track `audiodownload_allowed` flag, and offers `mp31` (96 kbps), `mp32` (VBR, good quality), OGG, and FLAC. The fresh metadata inventory and artist-grouped 800-ID manifest are now frozen and hash-linked. The extractor uses the per-track file endpoint as the final permission check; if it refuses an ID, the run stops and requires inventory/manifest refresh, with no replacement. OGG files are temporary; only pooled features and manifests persist. During a duplicate bulk metadata diagnostic, 8 of 16 50-ID batches returned empty results despite the fresh inventory marking them eligible, so the extractor does not repeat that flaky metadata query as a hard preflight. Sources: [Jamendo `/tracks/file` API](https://developer.jamendo.com/v3.0/tracks/file), [Jamendo track metadata and format options](https://developer.jamendo.com/v3.0/tracks).

**Five-track format pilot (2026-09-24):** the sample contains five fixed download-allowed tracks from the pinned clean human-annotation set, one per artist. It compares mp32, OGG, and FLAC; rotates format order across tracks; and uses the same absolute 10-second midpoint window across formats for each track. All 15 temporary audio files were deleted after processing. The script hard-codes these IDs; its recorded seed does not select them, so the sample is not evidence of a representative random draw. Per-track results and cleanup evidence are in [the five-track report](../../music%20understanding/reports/audio_format_pilot_5track.json).

| Format | Mean bitrate | Median size/min | Median download/min | Mean feature cosine vs. FLAC | Mean mel RMSE vs. FLAC |
|---|---:|---:|---:|---:|---:|
| MP32 | 200.9 kbps | 1.478 MB | 4.425 s | 0.9945 | 0.2276 |
| OGG | 116.8 kbps | 0.857 MB | 2.885 s | 0.9962 | 0.0826 |
| FLAC | 892.4 kbps | 6.608 MB | 15.818 s | 1.0000 | 0.0000 |

Decode/resample plus the DyMN frontend averaged 0.071–0.072 s for the lossy formats; model inference added about 0.057 s. OGG had a higher feature cosine than MP32 on three of five tracks, a lower median feature distance, and lower mean mel error (0.0826 vs. 0.2276); its mel error was lower on four of five tracks, with MP32 closer on `track_1061469`. Its mean size per minute was about 42% lower than MP32. For this frozen-backbone input and device, OGG is the selected extraction format. This is still only five fixed tracks and one window each: do not treat codec similarity as listening quality or downstream task accuracy. Validate task metrics on held-out validation data before scaling beyond the small frozen-feature baseline; revisit the selected codec only if an observed failure justifies it.

**Precomputed-feature fit:** MTG supplies full-dataset mel files (229 GB) and a mood/theme subset (68 GB), but these are not inputs for our selected DyMN04-AS checkpoint. MTG's pinned mel recipe is mono 12 kHz, 512-sample FFT, 256-sample hop, and 96 bands; our verified DyMN frontend requires a 32 kHz waveform and computes its own 128-band Kaldi mel representation with different windowing, pre-emphasis, and normalization. There is no verified compatible precomputed DyMN feature set in this workspace. Use the checkpoint's pooled 384-value output, not MTG's mels or 527 AudioSet logits. Sources: [MTG mel implementation](https://github.com/MTG/mtg-jamendo-dataset/blob/cafd8e20c265ed84f1e61f1c875327971f43a62f/scripts/melspectrograms.py), [MTG audio/precomputed data sizes](https://github.com/MTG/mtg-jamendo-dataset#downloading-the-data), [verified Wavv backbone contract](../../music%20understanding/reports/backbone_contract.json).

## Emotion data and distribution constraints

The [DEAM manual](https://cvml.unige.ch/databases/DEAM/manual.pdf) documents 744 development tracks, 1,000 2014 evaluation tracks, and 58 2015 evaluation tracks, with 45-second excerpts plus full songs and dynamic labels in [-1, 1]. The pinned metadata/annotation audit confirms all 1,802 track IDs align in both dynamic arousal and valence files; they begin at 15 seconds and advance every 500 ms. The manual says 2015 dynamic labels are more reliable, especially valence on the 2015 evaluation set. Use development data for fitting and keep evaluation labels untouched; align excerpt offsets and label timestamps, and carry supplied uncertainty into evaluation. Since DEAM includes Jamendo recordings and MTG-Jamendo is Jamendo-sourced, deduplicate recordings across the two datasets before any split. This duplicate check remains open because no corpus audio is retained and the pinned MTG metadata has no title/artist strings for a metadata join.

## Minimal validation gates

1. **Artifact gate:** pin source revision/checkpoint and hash; record runtime, input contract, outputs/features, and a fixed audio fixture. Verify finite outputs, expected shapes, and deterministic extraction against the official implementation. This CPU contract passes; the user manages source terms separately.
2. **Data gate:** passes for the initial 800-track human-label baseline. TSV/hash drift, special labels, per-class support, Jamendo availability, and the custom artist-disjoint split are reported in `data_audit.json`, `jamendo_availability.json`, and `mtg_human_manifest.json`. No weak-label head is supported at this cap. The 2,500/750/1,000 official weak-tag sample is not part of this custom split. The 9-track extractor smoke check passes; Gate 2A remains open until all 800 feature rows pass the full cache audit. DEAM duplicate checks remain a prerequisite only before DEAM is later added.
3. **Frozen-head gate:** train the smallest suitable heads on a small pipeline slice, then run the frozen baseline. Compare with a majority/prior baseline. Report per-task metrics and support: multi-label MTG tags with mAP and per-label precision/recall; single-label human genre with macro-F1/confusion; binary human tasks with AP/F1; DEAM regression with MAE/RMSE/correlation. Select thresholds only on validation.
4. **Final evaluation gate:** evaluate selected human-label tasks on their artist-held-out groups, weak uploader tags on the reserved MTG sample, and valence/arousal on untouched DEAM evaluation data. Keep scores per task and report supports/uncertainty. Only then decide whether to expand training, selectively fine-tune, choose window aggregation, or export for device inference.

Current documentation's architecture separation, frozen-first policy, compact label intent, and windowed song analysis remain sound, with the first baseline scope narrowed by measured support and transfer cost. The 800-track OGG-to-feature pipeline is underway; no training has run and no training entry point exists. Training may begin only after the full 800-row SQLite cache is finite, repeatable, manifest-aligned, integrity-checked, and leaves no audio behind. The user handles source terms manually. No public source establishes Wavv-task accuracy for this proposed model; that must be measured against validation and held-out baselines.
