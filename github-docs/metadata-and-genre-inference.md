# Local audio metadata and inferred genres

**Research snapshot:** 2026-10-14
**Scope:** Source-backed design findings and an implementation summary. This note intentionally excludes dataset names/sources and private model provenance. The repository's `docs/` tree is locally excluded, so this GitHub-safe note is in `github-docs/`.

## Findings

### Metadata without decoding a full track

Prefer metadata Android has already indexed. `MediaStore.Audio.Media` exposes fields including title, artist, album, genre, composer, album artist, year, track/disc number, duration, bitrate, MIME type, size, and modification time; audio columns also include sample rate and recording/music classifications. Wavv queries supported indexed fields, separately reads MediaStore genre membership, and uses `MediaMetadataRetriever` as an embedded-field/artwork fallback in [MediaLibraryRepository](../app/src/main/java/com/wavv/app/MediaLibraryRepository.kt). The expanded catalog includes author, writer, compilation, bitrate, disc number, sample rate, and track count where supplied; selected document sources use the same embedded fields.

The values are persisted through the Room 8→9 migration and used selectively: creator/release/technical text is searchable, album artist groups albums, track/disc numbers provide album ordering, and file tags populate playback metadata. The catalog also retains recording date and track count when available. File genres and model-inferred genres remain separate in storage. Missing or unsupported values remain unknown; coverage is not uniform across containers, Android versions, or document providers.

For user-selected files/folders, keep using content URIs and provider access rather than assuming filesystem paths. SAF providers can expose local, removable, or remote documents and support persistent grants; their metadata and performance can differ. [Storage Access Framework](https://developer.android.com/guide/topics/providers/document-provider)

When indexed fields are missing, `MediaMetadataRetriever` can read its documented metadata keys and optional embedded picture. It is not a universal raw-tag API: unsupported keys return null, and if a file has multiple pictures the API may return any one. Media3's `MetadataRetriever` can inspect metadata and tracks without creating a player, asynchronously, for media formats supported by Media3. `MediaExtractor.getTrackFormat()` can supply technical track properties such as MIME, sample rate, channels, and duration without asking Wavv to decode audio samples. These APIs support metadata-only inspection, but their contracts do **not** guarantee bounded I/O or promise that every format/provider can be inspected without reading substantial file data; this caution is an inference from the documented API scope, not a platform performance guarantee. Avoid describing the path as “never reads/decodes the file”; verify supported formats and keep extraction cancellable and off the UI thread. [MediaMetadataRetriever](https://developer.android.com/reference/android/media/MediaMetadataRetriever) · [Media3 Inspector](https://developer.android.com/media/media3/inspector) · [Media3 MetadataRetriever](https://developer.android.com/reference/androidx/media3/inspector/MetadataRetriever) · [MediaExtractor track formats](https://developer.android.com/reference/android/media/MediaExtractor#getTrackFormat(int))

**Recommendation:** keep reads staged: indexed columns first, then supported embedded values; defer artwork-byte reads until needed and bound image memory. Represent absent or unsupported fields as unknown. Keep audio decoding for separate embedding/tag analysis jobs, not ordinary library refresh. Per-field provenance and a full raw-tag browser are not implemented.

### Model genres should be additive, multi-label estimates

Genres can co-occur, so keep each predicted genre as its own annotation; do not force a single winner and do not overwrite embedded genre tags. In this checkout, `MusicTagger` produces independent sigmoid outputs and applies per-label thresholds ([MusicUnderstanding](../app/src/main/java/com/wavv/app/MusicUnderstanding.kt)); `withMusicUnderstandingGenres` adds above-threshold predictions to the genre view ([GenreCategories](../app/src/main/java/com/wavv/app/GenreCategories.kt)). A sigmoid output or a chosen threshold alone does not prove probability calibration. A 2024 multi-label calibration paper reports that common multi-label losses can yield poorly calibrated scores and evaluates calibration-specific methods; calibration must be measured for the actual labels and target population. [CVPR 2024 multi-label calibration paper](https://openaccess.thecvf.com/content/CVPR2024/papers/Cheng_Towards_Calibrated_Multi-label_Deep_Neural_Networks_CVPR_2024_paper.pdf) · [Neural-network calibration paper](https://proceedings.mlr.press/v70/guo17a.html)

Treat each label as a separate binary decision. On representative, human-checked, artist-disjoint validation data, assess per-label reliability (reliability plots plus a proper probability score such as Brier/log loss), then calibrate per label if it improves held-out reliability. Select each display/category threshold separately for the desired precision/recall trade-off; do not tune calibration or thresholds on the final test set. Sparse labels, annotation ambiguity, class imbalance, domain shift, and a small validation sample can make both calibration and thresholds unstable. Keep a label unknown rather than showing weak predictions as facts. Wavv applies the model's stored per-label threshold and uses model scores as soft ranking weights; this is score-weighting, not a claim that the scores are calibrated probabilities. [Strictly proper scoring rules](https://doi.org/10.1198/016214506000001437)

### Recommendations should consume annotations as evidence, not truth

Use embedded tags as explicit metadata evidence; use inferred genres as soft item-content features for search/category eligibility and recommendation ranking. A model score estimates its label output only to the extent demonstrated by calibration; it is not the probability that the listener likes the track. Likewise, DCLAP cosine similarity is an embedding-space closeness score, not a probability of relevance or satisfaction ([on-device analysis guide](on-device-analysis.md)). Keep those quantities distinct from behavioral preference signals. Genre tags feed the genre feature once; non-genre model tags feed a separate tag feature, with the inferred genre score weighting both candidate and taste evidence.

Keep predictions from changing the user's explicit tags, playlists, or taste profile by themselves. User actions establish preference; model annotations describe candidate content. Evaluate each source ablation against a simple metadata-and-listening baseline using time-ordered replay, per-label ranking/precision metrics, calibration, and repeat/diversity checks. Report recommendation output as an ordering or match rationale, never as “X% chance you will like this.”

## Limits and verification boundary

This is a static source-and-literature review, not device validation. Android extractors, document providers, and embedded-tag support vary by format and OS. Before claiming broad metadata coverage or calibrated genre confidence, test a format matrix with missing, conflicting, malformed, and multiple-image tags; verify cancellation, file changes/revoked URI grants, and memory bounds; and run held-out per-label calibration/evaluation. No claims are made here about the model's genre accuracy.
